The Monotonic Queue — Window Extremes in O(1)

A deque maintained in monotone order so that every sliding-window maximum or minimum query returns in constant time. One of the sharpest tricks in competitive programming.

O(n) total Amortized O(1) per query Deque + Monotone Invariant Sliding Window Stack Variant Queue Variant
01

The Core Insight

Imagine you're tracking the max of every 3-element window in a million-element array. A naïve scan through each window is O(n·k) — too slow. A heap costs O(n log k) with messy deletion. The monotonic deque gives you O(n) total, and the insight is beautiful:

Core Insight

If element A enters the window before element B, and A ≤ B, then A can never be the window maximum while B is alive. A is useless — remove it forever.

This "uselessness" is the elimination argument. By purging dominated elements on every insert, you maintain a deque in strictly decreasing order (for max queries). The front is always the window maximum. No element is pushed or popped more than once across all windows — total work is O(n).

Why the Elimination is Safe

Suppose we pop index i because a larger value arrived at index j > i. For any future window that includes index j, it must have entered after j entered — so j is present and dominates i. For any window that doesn't include j, it also can't include i (since i < j and both are within the same window range). So popping i is always safe.

The same idea works for minimum queries (maintain an increasing deque), for monotonic stacks (no expiry logic needed), and for constrained window problems where the invariant is more complex than simple max/min.

Recognition Pattern

If you see "maximum/minimum of every window of size k" or "longest subarray where max − min ≤ limit", think monotonic deque first. The tell is that you need extremes of a sliding window efficiently.

02

The Four Patterns

Monotonic deques and stacks appear in four distinct configurations. Recognizing which pattern applies is the skill — the implementation then follows mechanically.

Pattern 1

Fixed-Window Maximum

Classic sliding max/min across a fixed-size window. Deque stores indices; pop front when stale, pop back when dominated.

239 · Sliding Window Maximum 643 · Max Avg Subarray I 1343 · K-size Sub-arrays Avg ≥ threshold
Pattern 2

Variable-Window with Monotone Constraint

Window shrinks from the left when a constraint (e.g., max − min ≤ limit) is violated. Maintain two deques simultaneously — one for max, one for min.

480 · Sliding Window Median 1438 · Longest Subarray |max−min| ≤ limit 2762 · Continuous Subarrays
Pattern 3

Monotonic Stack (Next Greater / Smaller)

No window to expire — just maintain a decreasing or increasing stack. Pop when the invariant breaks to find the previous/next greater element.

496 · Next Greater Element I 739 · Daily Temperatures 84 · Largest Rectangle in Histogram 85 · Maximal Rectangle
Pattern 4

Prefix-Sum + Monotone Deque (DP Optimization)

Deque accelerates a DP recurrence where you need the optimal prior state inside a window. The deque replaces an O(k) inner loop with O(1) amortized.

862 · Shortest Subarray with Sum ≥ K 1425 · Constrained Subsequence Sum 918 · Max Circular Subarray Sum

The Deque Skeleton

All four patterns share the same core structure. The only variation is what you pop on the back (≥ for max, ≤ for min) and whether you expire the front.

monotonic_deque_skeleton 
import java.util.ArrayDeque;
import java.util.Deque;

// Pattern 1: Sliding window maximum (fixed k)
public int[] slidingWindowMax(int[] nums, int k) {
    Deque<Integer> dq = new ArrayDeque<>(); // stores INDICES
    int[] result = new int[nums.length - k + 1];
    int ri = 0;

    for (int i = 0; i < nums.length; i++) {
        // 1. Expire front if outside window
        if (!dq.isEmpty() && dq.peekFirst() < i - k + 1)
            dq.pollFirst();

        // 2. Maintain decreasing order: pop dominated elements
        while (!dq.isEmpty() && nums[dq.peekLast()] <= nums[i])
            dq.pollLast();

        dq.addLast(i);

        // 3. Front of deque = window max (once window is full)
        if (i >= k - 1)
            result[ri++] = nums[dq.peekFirst()];
    }
    return result;
}
from collections import deque

# Pattern 1: Sliding window maximum (fixed k)
def sliding_window_max(nums: list[int], k: int) -> list[int]:
    dq = deque()  # stores INDICES
    result = []

    for i, val in enumerate(nums):
        # 1. Expire front if outside window
        if dq and dq[0] < i - k + 1:
            dq.popleft()

        # 2. Maintain decreasing order: pop dominated elements
        while dq and nums[dq[-1]] <= val:
            dq.pop()

        dq.append(i)

        # 3. Front = window max (once window is full)
        if i >= k - 1:
            result.append(nums[dq[0]])

    return result
Common Gotcha

Always store indices in the deque, not values. You need indices both to expire stale elements (front < i−k+1) and to retrieve the answer (nums[dq.peekFirst()]). Storing values directly makes expiry impossible.

What to Watch For

Notice that when index 4 (value 5) enters, it pops indices 2 and 3 (values −1, −3) off the back — they're useless while 5 is alive. The deque never grows beyond k=3 elements. Each index is pushed once and popped at most once: total O(n) work.

Deep Dives

Two problems that reveal the full power of monotonic deques — one using the classic pattern and one combining prefix sums with the deque to optimize a DP transition.

Deep Dive 1

1438 · Longest Continuous Subarray with Absolute Diff ≤ Limit Hard

Find the longest subarray where max(subarray) − min(subarray) ≤ limit. This requires both the window maximum and window minimum simultaneously, and the window size is variable.

Key Observation

Maintain two monotonic deques: one decreasing (tracks max) and one increasing (tracks min). When max_deque.front − min_deque.front > limit, advance the left pointer and expire stale fronts from both deques.

1438_longest_subarray_abs_diff
public int longestSubarray(int[] nums, int limit) {
    Deque<Integer> maxDq = new ArrayDeque<>(); // decreasing → front is max
    Deque<Integer> minDq = new ArrayDeque<>(); // increasing → front is min
    int left = 0, ans = 0;

    for (int right = 0; right < nums.length; right++) {
        // Maintain max deque
        while (!maxDq.isEmpty() && nums[maxDq.peekLast()] <= nums[right])
            maxDq.pollLast();
        maxDq.addLast(right);

        // Maintain min deque
        while (!minDq.isEmpty() && nums[minDq.peekLast()] >= nums[right])
            minDq.pollLast();
        minDq.addLast(right);

        // Shrink window while constraint violated
        while (nums[maxDq.peekFirst()] - nums[minDq.peekFirst()] > limit) {
            if (maxDq.peekFirst() == left) maxDq.pollFirst();
            if (minDq.peekFirst() == left) minDq.pollFirst();
            left++;
        }

        ans = Math.max(ans, right - left + 1);
    }
    return ans;
}
from collections import deque

def longest_subarray(nums: list[int], limit: int) -> int:
    max_dq = deque()  # decreasing → front is max
    min_dq = deque()  # increasing → front is min
    left = ans = 0

    for right, val in enumerate(nums):
        # Maintain max deque
        while max_dq and nums[max_dq[-1]] <= val:
            max_dq.pop()
        max_dq.append(right)

        # Maintain min deque
        while min_dq and nums[min_dq[-1]] >= val:
            min_dq.pop()
        min_dq.append(right)

        # Shrink window while constraint violated
        while nums[max_dq[0]] - nums[min_dq[0]] > limit:
            if max_dq[0] == left: max_dq.popleft()
            if min_dq[0] == left: min_dq.popleft()
            left += 1

        ans = max(ans, right - left + 1)

    return ans

Complexity: O(n) time — each index enters and exits each deque at most once. O(k) space where k is the answer window size.

Deep Dive 2

862 · Shortest Subarray with Sum ≥ K Hard

Find the length of the shortest (contiguous) subarray whose sum is ≥ K. The catch: values can be negative, so simple two-pointer shrinking fails. The insight is to convert to prefix sums, then use a monotone deque to find the optimal left boundary efficiently.

The Elimination Argument

If prefix[j] ≥ prefix[i] for i < j, then index i is a better left boundary than j for any future right pointer (same or better sum, but the answer length would be longer from j). So we never need j as a left endpoint if prefix[i] ≤ prefix[j].

862_shortest_subarray_sum_k
public int shortestSubarray(int[] nums, int k) {
    int n = nums.length;
    long[] prefix = new long[n + 1];
    for (int i = 0; i < n; i++)
        prefix[i + 1] = prefix[i] + nums[i];

    Deque<Integer> dq = new ArrayDeque<>(); // stores prefix indices, increasing prefix values
    int ans = Integer.MAX_VALUE;

    for (int right = 0; right <= n; right++) {
        // Pop from front while subarray sum ≥ k: record and shrink
        while (!dq.isEmpty() && prefix[right] - prefix[dq.peekFirst()] >= k)
            ans = Math.min(ans, right - dq.pollFirst());

        // Maintain increasing prefix values: pop dominated back
        while (!dq.isEmpty() && prefix[dq.peekLast()] >= prefix[right])
            dq.pollLast();

        dq.addLast(right);
    }
    return ans == Integer.MAX_VALUE ? -1 : ans;
}
from collections import deque

def shortest_subarray(nums: list[int], k: int) -> int:
    n = len(nums)
    prefix = [0] * (n + 1)
    for i, v in enumerate(nums):
        prefix[i + 1] = prefix[i] + v

    dq = deque()  # stores prefix indices, increasing by prefix value
    ans = float('inf')

    for right in range(n + 1):
        # Pop from front while sum ≥ k: record shortest
        while dq and prefix[right] - prefix[dq[0]] >= k:
            ans = min(ans, right - dq.popleft())

        # Maintain increasing prefix values
        while dq and prefix[dq[-1]] >= prefix[right]:
            dq.pop()

        dq.append(right)

    return ans if ans != float('inf') else -1

Complexity: O(n) time. The deque-optimized approach avoids the O(n²) brute force and the O(n log n) heap approach. Space is O(n) for the prefix array.

Pattern 1 · Fixed-Window Maximum · Observability / SRE

Rolling Latency Budget Monitor

Your SRE team needs to alert when any rolling 5-minute window of API requests contains a peak P99 latency above the SLA threshold. Given a time-series array of per-request latency values (milliseconds) and a window size k, return the maximum latency for every consecutive window of size k. An alert fires if any returned value exceeds the threshold.

Example
latencies = [120, 340, 85, 910, 200, 150, 670, 430] k = 3 Output: [340, 910, 910, 910, 670, 670] — window [120,340,85] → 340, [340,85,910] → 910, etc.
  • 1 ≤ n ≤ 10⁶
  • 1 ≤ latency ≤ 10⁵
  • 1 ≤ k ≤ n
  • O(n) time required

Why this pattern?

Each window's SLA check only needs the maximum latency in that window. A naïve max-scan is O(n·k) and will lag on a million-event stream. The monotonic deque delivers the max of every window in amortized O(1) — the back is purged of dominated requests, and the front always holds the worst offender in the current window.

rolling_latency_monitor
import java.util.*;

public class LatencyMonitor {
    /**
     * Returns the max latency in every window of size k.
     * Fire alert if any value exceeds slaThresholdMs.
     */
    public int[] rollingMaxLatency(int[] latencies, int k, int slaThresholdMs) {
        Deque<Integer> dq = new ArrayDeque<>();
        int n = latencies.length;
        int[] windowMaxes = new int[n - k + 1];
        int ri = 0;

        for (int i = 0; i < n; i++) {
            // Expire requests that fell out of the k-request window
            if (!dq.isEmpty() && dq.peekFirst() < i - k + 1)
                dq.pollFirst();

            // Drop requests dominated by the current (they can never be peak)
            while (!dq.isEmpty() && latencies[dq.peekLast()] <= latencies[i])
                dq.pollLast();

            dq.addLast(i);

            if (i >= k - 1) {
                windowMaxes[ri] = latencies[dq.peekFirst()];
                if (windowMaxes[ri] > slaThresholdMs)
                    System.err.println("SLA BREACH at window ending index " + i
                        + ": peak=" + windowMaxes[ri] + "ms");
                ri++;
            }
        }
        return windowMaxes;
    }
}
from collections import deque

def rolling_max_latency(
    latencies: list[int], k: int, sla_threshold_ms: int
) -> list[int]:
    """Returns the max latency in every window of size k.
    Logs SLA breach events to stderr."""
    import sys
    dq = deque()
    window_maxes = []

    for i, lat in enumerate(latencies):
        # Expire stale requests
        if dq and dq[0] < i - k + 1:
            dq.popleft()

        # Drop dominated requests off the back
        while dq and latencies[dq[-1]] <= lat:
            dq.pop()

        dq.append(i)

        if i >= k - 1:
            peak = latencies[dq[0]]
            window_maxes.append(peak)
            if peak > sla_threshold_ms:
                print(f"SLA BREACH at window ending {i}: peak={peak}ms",
                      file=sys.stderr)

    return window_maxes
Pattern 2 · Variable-Window Constraint · Trading Systems

Trading Volatility Band Filter

A trading risk system must flag the longest contiguous sequence of price ticks where the spread between the highest and lowest tick stays within a volatility band limit. Given a list of integer price ticks and a band limit, return the length of the longest such run. This drives position-sizing models: wider stable windows mean larger allowed positions.

Example
ticks = [10, 12, 9, 11, 14, 8, 13, 12] limit = 4 Output: 4 (subarray [10,12,9,11] has spread 12-9=3 ≤ 4)
  • 1 ≤ n ≤ 10⁵
  • 0 ≤ ticks[i] ≤ 10⁸
  • 0 ≤ limit ≤ 10⁸
  • O(n) time required

Why this pattern?

Two deques track the rolling max and rolling min simultaneously. When the spread exceeds limit, we advance the left pointer and retire any front elements that have left the window. This is the dual-deque variable window pattern — neither pointer moves backwards, giving amortized O(1) per step.

trading_volatility_band
public int longestStableRun(int[] ticks, int limit) {
    Deque<Integer> maxDq = new ArrayDeque<>(); // decreasing
    Deque<Integer> minDq = new ArrayDeque<>(); // increasing
    int left = 0, ans = 0;

    for (int right = 0; right < ticks.length; right++) {
        // Update max deque
        while (!maxDq.isEmpty() && ticks[maxDq.peekLast()] <= ticks[right])
            maxDq.pollLast();
        maxDq.addLast(right);

        // Update min deque
        while (!minDq.isEmpty() && ticks[minDq.peekLast()] >= ticks[right])
            minDq.pollLast();
        minDq.addLast(right);

        // Contract window until spread ≤ limit
        while (ticks[maxDq.peekFirst()] - ticks[minDq.peekFirst()] > limit) {
            if (maxDq.peekFirst() == left) maxDq.pollFirst();
            if (minDq.peekFirst() == left) minDq.pollFirst();
            left++;
        }
        ans = Math.max(ans, right - left + 1);
    }
    return ans;
}
from collections import deque

def longest_stable_run(ticks: list[int], limit: int) -> int:
    max_dq = deque()  # decreasing — front is running max
    min_dq = deque()  # increasing — front is running min
    left = ans = 0

    for right, price in enumerate(ticks):
        while max_dq and ticks[max_dq[-1]] <= price:
            max_dq.pop()
        max_dq.append(right)

        while min_dq and ticks[min_dq[-1]] >= price:
            min_dq.pop()
        min_dq.append(right)

        # Shrink until volatility band ≤ limit
        while ticks[max_dq[0]] - ticks[min_dq[0]] > limit:
            if max_dq[0] == left: max_dq.popleft()
            if min_dq[0] == left: min_dq.popleft()
            left += 1

        ans = max(ans, right - left + 1)

    return ans
Pattern 3 · Monotonic Stack · DevOps / Capacity Planning

Service Wait-Time Attribution

In a distributed trace, each microservice call has a duration. For each call, find the next call that is longer in duration (the "next bottleneck"). This power the "critical path highlighting" feature of your APM tool — every span is annotated with how far ahead the next slower span is. Given an array of call durations, return an array where result[i] = number of steps to the next greater duration (0 if none exists).

Example
durations = [73, 74, 75, 71, 69, 72, 76, 73] Output: [1, 1, 4, 2, 1, 1, 0, 0] — durations[0]=73, next greater is durations[1]=74, distance=1
  • 1 ≤ n ≤ 10⁵
  • 30 ≤ durations[i] ≤ 10⁴
  • O(n) time, O(n) space

Why this pattern?

This is LeetCode 739 (Daily Temperatures) in a tracing disguise. We maintain a decreasing monotonic stack of unresolved indices. When a new (larger) value arrives, every smaller element at the top of the stack has found its "next greater" — we pop and record the distance. No element is pushed or popped more than once: O(n) total.

next_bottleneck_attribution
public int[] nextBottleneck(int[] durations) {
    int n = durations.length;
    int[] result = new int[n];
    Deque<Integer> stack = new ArrayDeque<>(); // indices, decreasing durations

    for (int i = 0; i < n; i++) {
        // Pop all spans for which current is the next bottleneck
        while (!stack.isEmpty() && durations[stack.peek()] < durations[i]) {
            int prev = stack.pop();
            result[prev] = i - prev; // distance to next bottleneck
        }
        stack.push(i);
    }
    // Remaining on stack have no next greater → result stays 0
    return result;
}
def next_bottleneck(durations: list[int]) -> list[int]:
    n = len(durations)
    result = [0] * n
    stack = []  # indices with decreasing durations

    for i, dur in enumerate(durations):
        # Pop all spans for which this is the next larger duration
        while stack and durations[stack[-1]] < dur:
            prev = stack.pop()
            result[prev] = i - prev

        stack.append(i)

    # Remaining have no next greater — result[i] stays 0
    return result
Pattern 4 · Prefix-Sum + Deque DP · Finance

Shortest Compliant Transaction Batch

A compliance system requires that every submitted batch of transactions have a net credit total of at least K to clear the settlement system. Given a signed integer array representing individual transaction values (negative = debit, positive = credit), find the length of the shortest contiguous batch whose sum is ≥ K. Returns −1 if no such batch exists.

Example
transactions = [2, -1, 2, 3, -2, 4, -1] K = 5 Output: 3 (subarray [3, -2, 4] sums to 5)
  • 1 ≤ n ≤ 10⁵
  • -10⁴ ≤ txn[i] ≤ 10⁴
  • 1 ≤ K ≤ 10⁹
  • O(n) time required

Why this pattern?

Negative values break the two-pointer approach (shrinking the window can actually increase the sum). Converting to prefix sums and maintaining an increasing prefix-value deque lets us find the optimal left boundary in O(1): we pop the front whenever prefix[right] − prefix[front] ≥ K, recording the shortest batch seen so far.

shortest_compliant_batch
public int shortestBatch(int[] txns, int K) {
    int n = txns.length;
    long[] prefix = new long[n + 1];
    for (int i = 0; i < n; i++)
        prefix[i + 1] = prefix[i] + txns[i];

    Deque<Integer> dq = new ArrayDeque<>(); // increasing prefix values
    int ans = Integer.MAX_VALUE;

    for (int right = 0; right <= n; right++) {
        // Find shortest batch ending at 'right'
        while (!dq.isEmpty() && prefix[right] - prefix[dq.peekFirst()] >= K)
            ans = Math.min(ans, right - dq.pollFirst());

        // Maintain increasing prefix deque
        while (!dq.isEmpty() && prefix[dq.peekLast()] >= prefix[right])
            dq.pollLast();

        dq.addLast(right);
    }
    return ans == Integer.MAX_VALUE ? -1 : ans;
}
from collections import deque

def shortest_batch(txns: list[int], K: int) -> int:
    n = len(txns)
    prefix = [0] * (n + 1)
    for i, v in enumerate(txns):
        prefix[i + 1] = prefix[i] + v

    dq = deque()  # indices with increasing prefix values
    ans = float('inf')

    for right in range(n + 1):
        while dq and prefix[right] - prefix[dq[0]] >= K:
            ans = min(ans, right - dq.popleft())

        while dq and prefix[dq[-1]] >= prefix[right]:
            dq.pop()

        dq.append(right)

    return ans if ans != float('inf') else -1

Mental Model

Think of the monotonic deque as a hall of champions. When a new contender arrives, it challenges everyone weaker at the back — those beaten champions are eliminated permanently, because they can never be champion while the new contender is in the window. The current champion sits at the front, ready to be dethroned only when they age out of the window entirely.

The stack variant is the same hall, but there's no aging out — champions hold their title until literally beaten. Each "pop" during insertion is both the champion's defeat and the new element's record of who it just beat (next-greater answers).

The prefix-sum + deque variant flips the lens: instead of tracking current extremes, you're scanning for the best past state to partner with the current index. The deque holds a sorted shortlist of left boundaries — you pop from the front greedily as valid partners are found, and pop from the back to discard useless future partners.

The One Mistake Everyone Makes

Using < vs <= on the back-pop condition. For strictly decreasing (max of window), pop when nums[back] <= nums[i] — equal values are dominated. For non-strictly decreasing (last occurrence of max), pop only when nums[back] < nums[i]. Check the problem statement carefully.

The Two-Line Invariant Check

Every monotonic deque can be described in two sentences: "The deque stores [indices/values] in [increasing/decreasing] order of [values/prefix-sums]. The front is always the [max/min/optimal] of the current window." If you can fill in those blanks before writing code, the implementation follows directly.

The Interview Sentence

"I'll use a monotonic deque — the key insight is that any element dominated by a newer element can never be the window extremum while that newer element is alive, so we can purge it immediately. This makes each element push and pop at most once, giving amortized O(1) per query and O(n) total — optimal for this class of sliding-window problems."
