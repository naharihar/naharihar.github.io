01 — FIRST PRINCIPLES

At every amount, you make
one of three decisions

Strip everything down to the decision model. You have a target amount A and a set of coin denominations. At any state a, you can:

PICK COIN
Choose c. Transition to a - c. Cost = 1 + f(a-c).
STOP
If a == 0, cost = 0. Success.
FAIL
If a < 0 or no valid c, cost = ∞.

That's it. The entire series is three problems and two techniques built on this single recurrence. The constraint changes the state space. The state space determines the algorithm.

Core Insight
The key question for every variant is: what states do I need to track to guarantee an optimal decision at each amount? Answer that, and the recurrence writes itself.

Let's build intuition by asking: why can't we just use greedy? For denominations like [1, 3, 4], picking 4 first for amount 6 leaves 2, requiring two 1s — total 3 coins. But 3 + 3 uses only 2. Greedy fails because coin systems aren't always canonical. We need a systematic way to explore all paths.

The escape is the optimal substructure property: f(a) = 1 + min(f(a-c)). If we know the optimal solution for smaller amounts, we can build up to A. This O(2^A) → O(A·n) reduction is the foundation of DP.

Elimination Argument
Suppose the optimal solution for amount A ends with coin c. Then the remaining A-c must also be solved optimally. If it weren't, we could swap in a better sub-solution and improve A — contradiction. Therefore, we only need to track the best cost to reach each amount.

PROBLEM 1 · #322

Min Coins — Tabulation

Initialize dp[0]=0, others=∞. Fill forward: dp[i] = min(dp[i], dp[i-c]+1). The answer is dp[A]. Simple, predictable, production-ready.

dpO(A) spaceMedium
PROBLEM 2 · #518

Count Ways — Loop Order

Outer loop = coin → combinations (order irrelevant). Outer loop = amount → permutations (order matters). The += replaces min+1 because we sum paths, not minimize costs.

dploop orderMedium
PROBLEM 3 · Bounded Knapsack

Limited Supply — 0/1 Knapsack DP

Each coin has a count limit. Iterate amounts backwards (like 0/1 knapsack) so each coin can only be used up to its stock limit. Unlimited supply uses forward iteration.

dpO(A·k) spaceHard

Track prev[i] = which coin gave dp[i]. Backtrack from A to 0 by following prev. Turns an abstract count into a concrete coin list. Not a separate LC problem — an extension of #322.

#322 Coin Change (Min Coins) Medium

Given an integer array coins representing coin denominations and an integer amount, return the fewest number of coins that you need to make up that amount. If that amount cannot be made up by any combination of the coins, return -1.

EXAMPLE 1
Input: coins = [1, 3, 4], amount = 6
Output: 2
// Explanation: 3 + 3 = 6 (2 coins)

The DP State Machine

Model the problem as filling a 1D array where each index represents an amount. You transition forward by trying every coin:

STATE: dp[i]
min coins to make amount i
TRANSITION
dp[i] = min(dp[i], dp[i-c] + 1)
BASE CASE
dp[0] = 0, others = ∞

Initialize dp[0] = 0, others = ∞. Iterate i from 1 to amount. For each coin c, if i >= c, update: dp[i] = min(dp[i], dp[i-c] + 1). The answer is dp[amount].

Gotcha
Using float('inf') in Python or Integer.MAX_VALUE in Java requires care. inf + 1 stays inf, but MAX_VALUE + 1 overflows to a negative number. The safe pattern in Java is to init with amount + 1 as the sentinel — it can never be a valid coin count, and it won't overflow.
LC #322 — Min Coins
class Solution {
  public int coinChange(int[] coins, int amount) {
    // dp[i] = min coins for amount i
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, amount + 1); // use amount+1 as safe infinity
    dp[0] = 0;

    for (int i = 1; i <= amount; i++) {
      for (int coin : coins) {
        if (i >= coin && dp[i - coin] != amount + 1) {
          dp[i] = Math.min(dp[i], dp[i - coin] + 1);
        }
      }
    }
    return dp[amount] > amount ? -1 : dp[amount];
  }
}
class Solution:
  def coinChange(self, coins: list[int], amount: int) -> int:
    dp = [amount + 1] * (amount + 1)
    dp[0] = 0

    for i in range(1, amount + 1):
      for coin in coins:
        if i >= coin:
          dp[i] = min(dp[i], dp[i - coin] + 1)

    return dp[amount] if dp[amount] <= amount else -1
#518 Coin Change II (Count Ways) Medium

Given an integer array coins representing coin denominations and an integer amount, return the number of combinations that make up that amount. If that amount cannot be made up, return 0.

EXAMPLE
Input: amount = 5, coins = [1, 2, 5]
Output: 4
// 5=2+2+1, 5=2+1+1+1, 5=1+1+1+1+1, 5=5

The Loop Order Revelation

COMBINATIONS — coins outer
for coin: for i: dp[i] += dp[i-coin]
PERMUTATIONS — amounts outer
for i: for coin: dp[i] += dp[i-coin]

Here's the precise reason: when coins is the outer loop, each denomination's entire contribution is resolved before the next coin is introduced. By the time we process coin=2, dp[3] already encodes all ways using only coin=1. So adding coin=2's contribution to dp[3] never sees a state where coin=2 was already counted — it can't double-count [1,2] and [2,1] as separate orderings, because both would arrive at the same dp state via the same monotone sequence of coin passes.

Flip the loops (amounts outer) and at each amount i you try every coin as the last step independently. dp[3] via coin=1 and dp[3] via coin=2 are both reachable in different orders, so [1,2] and [2,1] count separately. That's #377 (Combination Sum IV).

LC #518 — Count Ways (Combinations)
class Solution {
  public int change(int amount, int[] coins) {
    int[] dp = new int[amount + 1];
    dp[0] = 1; // one way to make 0: pick nothing

    // 🔑 FIXES canonical coin order
    for (int coin : coins) {
      for (int i = coin; i <= amount; i++) {
        dp[i] += dp[i - coin];
      }
    }
    return dp[amount];
  }
}
class Solution:
  def change(self, amount: int, coins: list[int]) -> int:
    dp = [0] * (amount + 1)
    dp[0] = 1

    # 🔑 FIXES canonical coin order
    for coin in coins:
      for i in range(coin, amount + 1):
        dp[i] += dp[i - coin]

    return dp[amount]

Problem 1 · Min Coins ATM Cash Dispensing Optimization Finance

An ATM must dispense a requested amount using the minimum number of physical bills/coins. It has a fixed set of denominations. Find the optimal combination to minimize mechanical wear and customer wait time.

EXAMPLE
denominations = [1, 5, 10, 25], requested = 63
Output: 6
// 25 + 25 + 10 + 1 + 1 + 1 (6 bills). While canonical systems like USD allow greedy, DP guarantees optimality for any non-canonical or constrained system.

Why DP: Real-world currency systems are often canonical, but embedded systems, vending machines, or custom token economies rarely are. DP guarantees optimality regardless of denomination structure.

ATM Dispensing · Min Bills
public int minBills(int[] denom, int amount) {
  int[] dp = new int[amount + 1];
  Arrays.fill(dp, amount + 1); dp[0] = 0;
  for (int i = 1; i <= amount; i++)
    for (int d : denom)
      if (i >= d) dp[i] = Math.min(dp[i], dp[i-d] + 1);
  return dp[amount] > amount ? -1 : dp[amount];
}
def min_bills(denom: list[int], amount: int) -> int:
  dp = [amount + 1] * (amount + 1)
  dp[0] = 0
  for i in range(1, amount + 1):
    for d in denom:
      if i >= d: dp[i] = min(dp[i], dp[i-d] + 1)
  return dp[amount] if dp[amount] <= amount else -1
Problem 2 · Count Ways Currency System Design & Validation Economics

A central bank wants to know how many distinct combinations of coin denominations can form a target value. This helps evaluate liquidity fragmentation and transaction complexity in a proposed denomination system.

EXAMPLE
Input: amount = 10, coins = [2, 5]
Output: 2
// 10 = 5 + 5 (two 5-cent coins) or 10 = 2+2+2+2+2 (five 2-cent coins)

Why combinations vs permutations: In economics, the order of denominations doesn't matter. A transaction using one 5 and two 2s is identical regardless of sequence. The coin-outer loop enforces this canonical counting.

Currency Validation · Count Combinations

}

Problem 3 · Bounded Knapsack Limited Packaging Inventory Logistics

A fulfillment center must ship exactly target pounds of goods for a specific order. They have a fixed inventory of standard box types, each with a known weight capacity. Find the minimum number of boxes needed to hit the exact target weight. If the current stock can't cover it, return -1.

REAL-WORLD SCENARIO
box_weights = [3, 5, 10]  →  Available box types (3lb, 5lb, 10lb)
inventory = [2, 1, 3]  →  How many of each are currently in stock
target = 8  →  Exact weight to ship
Output: 2  →  // One 5lb box + One 3lb box = 8lb (uses 2 boxes total)

Why This Constraint Exists in Real Life:
Warehouses don't have infinite boxes. They're limited by what's physically on the shelves. The algorithm must track how many of each box type you've already used, ensuring you never exceed the available inventory. It tries every valid combination (0 to max_stock of each type) and picks the one that hits the target with the fewest boxes.

How it maps to DP: This is coin change with a supply limit. The DP state tracks the best solution using the first k box types. For each type, you iterate through possible counts (0 to inventory[k]) and update the table accordingly. This transforms the problem into a bounded knapsack variant.

Mapping Back to LeetCode
Unlimited boxes → LC #322 (standard coin change). Limited boxes → bounded knapsack DP (iterate backwards per coin). The core recurrence is identical; only the per-item count constraint changes.
Limited Packaging · Bounded DP
public int minBoxes(int[] sizes, int[] stock, int target) {
  int[] dp = new int[target + 1];
  Arrays.fill(dp, target + 1); dp[0] = 0;

  for (int k = 0; k < sizes.length; k++) {
    // Iterate backwards to simulate bounded knapsack
    for (int i = target; i >= sizes[k]; i--) {
      for (int c = 1; c <= stock[k] && i - c * sizes[k] >= 0; c++) {
        dp[i] = Math.min(dp[i], dp[i - c * sizes[k]] + c);
      }
    }
  }
  return dp[target] > target ? -1 : dp[target];
}
def min_boxes(sizes: list[int], stock: list[int], target: int) -> int:
  dp = [target + 1] * (target + 1)
  dp[0] = 0
  for k in range(len(sizes)):
    for i in range(target, sizes[k] - 1, -1):
      for c in range(1, stock[k] + 1):
        if i - c * sizes[k] >= 0:
          dp[i] = min(dp[i], dp[i - c * sizes[k]] + c)
  return dp[target] if dp[target] <= target else -1

Start: LC #322 (Medium)

Internalize the tabulation recurrence. Can you derive dp[i] = min(dp[i], dp[i-c]+1) from first principles without looking anything up? If yes, you've got the DP foundation.

LC #518 (Medium)

Prove to yourself why outer loop = coin gives combinations. Write both loop orders and verify they produce different outputs on [1,2], amount=3.

Technique: Path Reconstruction (#322 extension)

Add a predecessor array to #322. Trace the example by hand once. The recurrence doesn't change — you just record the winning coin at each step.

Bounded Knapsack (Hard)

Introduce stock limits. The backwards iteration mimics 0/1 knapsack. The key insight: iterating backwards prevents the same item from being counted twice in one pass.

Technique: BFS (#322 alternative)

Model amounts as nodes, each coin as an edge. Level-order traversal guarantees shortest path. Often faster in practice due to early exit before filling the full table.

07 — MENTAL MODEL

The question behind
every variant

Every problem in this series asks the same thing in disguise: given my current amount, what is the optimal cost/value to reach 0 from here? The DP state is just a formal encoding of "my current position in the decision tree."

For tabulation (min coins), the optimal position at each step can be derived from only local information. For counting or bounded variants, the optimal position depends on history — so we carry that history forward explicitly as state variables or loop order.

The progression from #322 → #518 → bounded knapsack → BFS is a progression in how much history matters. When history doesn't matter, greedy/tabulation wins. When it does, DP carries it.

The Single Rule
For each amount: if you could have predicted this coin selection, would you be at the optimal sub-state right now? If unlimited supply — yes. If bounded — check stock. If counting — sum all valid paths. The DP state is just a compact answer to that question at every step.
Interview Signal Sentence
"I model this as a state machine where each amount tracks the optimal cost/ways to reach 0. The constraint — whether it's bounded supply, counting combinations, or path reconstruction — determines how many states I need and how they transition. The recurrence falls out directly: each state either holds or advances, and I take the min/sum."
