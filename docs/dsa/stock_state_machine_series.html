01 — THE HIDDEN VARIABLE

Three factors,
not two

Most people think the state for these problems is just (day, transactions left). That's incomplete. The missing factor — the one that controls what actions are legal — is whether you're currently holding stock.

You can't buy if you're already holding. You can't sell if you're not. So every state splits in two: T[i][k][0] (max profit ending day i, k transactions left, not holding) and T[i][k][1] (same, but holding). Once you accept this, the recurrence writes itself.

Core Insight
T[i][k][0] — you can rest (do nothing) or sell today.
T[i][k][1] — you can rest (do nothing) or buy today.
Pick whichever maximizes profit. That's the entire algorithm.

The universal recurrence — four lines that cover every stock problem before any specialization:

UNIVERSAL RECURRENCE (T[i][k][0/1])
T[i][k][0] = max( T[i-1][k][0],   T[i-1][k][1] + price[i] )
                      ↑ rest               ↑ sell today

T[i][k][1] = max( T[i-1][k][1],   T[i-1][k-1][0] − price[i] )
                      ↑ rest               ↑ buy today (k decrements)
Why k decrements on buy, not sell?
A transaction = one buy + one sell pair. We count it as "used" the moment we buy — that's when we commit capital. This convention is consistent and arbitrary; you could decrement on sell instead as long as you adjust the base cases. Both work.
Base Cases
T[-1][k][0] = 0 — no days yet, no profit. Fine.
T[-1][k][1] = −∞ — can't be holding before day 0. Impossible state.
T[i][0][0] = 0 — no transactions left, no profit.
T[i][0][1] = −∞ — can't be holding with 0 transactions. Impossible.
The −∞ values are guards — when you take max(), impossible states always lose.

Single Transaction

Since k=1 always, T[k-1][0] = T[0][0] = 0 (base case). The buy line collapses to max(hold, −price) — just tracking the cheapest buy seen so far.

CASE 2 · #122 · k = ∞

Unlimited Transactions

When k=∞, k and k−1 are indistinguishable, so T[k-1][0] = T[k][0] = cash. Both recurrences reference the same k. Collapses to 2 symmetric variables.

2 varsgreedy possibleMedium
CASE 3 · #123 · k = 2

At Most 2 Transactions

Four variables: T[1][0], T[1][1], T[2][0], T[2][1]. They chain — k=2 buy reads from k=1 sell. Update in reverse order to avoid using stale values.

CASE 4 · #188 · k = K

At Most K Transactions

Generalize case 3 to K. Use two arrays of size K+1. Key optimization: if k ≥ n/2, collapse to k=∞ solution (can't have more than n/2 profitable trades in n days).

#123 Best Time to Buy and Sell Stock III Hard

You are given an array prices where prices[i] is the price on day i. Find the maximum profit you can achieve with at most two transactions. You may not hold more than one stock at a time.

EXAMPLE
Input: prices = [3, 3, 5, 0, 0, 3, 1, 4]
Output: 6
// Buy day 4 (price=0), sell day 6 (price=3) = +3. Buy day 7 (price=1), sell day 8 (price=4) = +3.

Why four variables, not two?

With k=2, k and k−1 are not interchangeable. We need to separately track profit at k=1 and k=2. The four states form a chain: k=2 buy can only happen after k=1 has been fully settled.

// States: T10 (k=1, not holding), T11 (k=1, holding), T20, T21
T20 = max(T20, T21 + price)   ← sell 2nd txn
T21 = max(T21, T10 − price)   ← buy 2nd txn (uses k=1 profit!)
T10 = max(T10, T11 + price)   ← sell 1st txn
T11 = max(T11, −price)       ← buy 1st txn (T[0][0] = 0)
Critical Gotcha
T21 = max(T21, T10 − price) — the second buy subtracts from T10, not zero. This means it carries forward the profit from the first transaction into the second. If you use −price instead, you'd restart from scratch and get wrong answers on cases where the two transactions overlap optimally.
LC #123 — At Most 2 Transactions
class Solution {
  public int maxProfit(int[] prices) {
    int T10 = 0, T11 = Integer.MIN_VALUE;
    int T20 = 0, T21 = Integer.MIN_VALUE;

    for (int price : prices) {
      // Update in reverse k order: k=2 first, then k=1
      // This ensures we read k=1 values from the PREVIOUS day
      T20 = Math.max(T20, T21 + price);
      T21 = Math.max(T21, T10 - price); // uses T10 from prev day
      T10 = Math.max(T10, T11 + price);
      T11 = Math.max(T11, -price);      // T[i-1][0][0] = 0
    }
    return T20;
  }
}
class Solution:
  def maxProfit(self, prices: list[int]) -> int:
    T10, T11 = 0, float('-inf')
    T20, T21 = 0, float('-inf')

    for price in prices:
      # Reverse k order so T10 is still from previous day
      T20 = max(T20, T21 + price)
      T21 = max(T21, T10 - price)
      T10 = max(T10, T11 + price)
      T11 = max(T11, -price)

    return T20
#309 Best Time to Buy and Sell Stock with Cooldown Medium

After you sell your stock, you cannot buy stock on the next day (i.e., cooldown period is 1 day). You may complete as many transactions as you like. Find the maximum profit.

EXAMPLE
Input: prices = [1, 2, 3, 0, 2]
Output: 3
// Buy day 1, sell day 3. Cooldown day 4. Buy day 5, sell day 5 — or: buy 1, sell 3, buy 5, sell 5 = 3.

The one-line change that breaks greedy

Start from k=∞ (LC #122). The buy transition normally uses cash from yesterday. With cooldown, you can't buy on the day after a sell — so the buy transition must reach back to two days ago: T[i-2][0].

k=∞ original:   hold = max(hold, cash − price)
cooldown:      hold = max(hold, prev_cash − price)  ← T[i-2][0]

We need one extra variable prev_cash that holds what cash was two days ago. Update it at the end of each day: prev_cash = old_cash before you overwrite cash.

LC #309 — Cooldown
class Solution {
  public int maxProfit(int[] prices) {
    int cash = 0, hold = Integer.MIN_VALUE, prevCash = 0;

    for (int price : prices) {
      int oldCash = cash;          // save before overwrite
      cash    = Math.max(cash, hold + price);
      hold    = Math.max(hold, prevCash - price); // T[i-2][0]!
      prevCash = oldCash;           // shift the window
    }
    return cash;
  }
}
class Solution:
  def maxProfit(self, prices: list[int]) -> int:
    cash, hold, prev_cash = 0, float('-inf'), 0

    for price in prices:
      cash, hold, prev_cash = (
        max(cash, hold + price),
        max(hold, prev_cash - price),  # T[i-2][0]
        cash                              # shift window
      )

    return cash

#188 · k=K · Arbitrary K
public int maxProfit(int k, int[] prices) {
  int n = prices.length;
  if (k >= n / 2) { // collapse to k=∞
    int cash = 0, hold = Integer.MIN_VALUE;
    for (int p : prices) {
      int prev = cash;
      cash = Math.max(cash, hold + p);
      hold = Math.max(hold, prev - p);
    }
    return cash;
  }
  int[] T0 = new int[k + 1]; // not holding per k level
  int[] T1 = new int[k + 1]; // holding per k level
  Arrays.fill(T1, Integer.MIN_VALUE);
  for (int p : prices)
    for (int j = k; j > 0; j--) {
      T0[j] = Math.max(T0[j], T1[j] + p);
      T1[j] = Math.max(T1[j], T0[j-1] - p);
    }
  return T0[k];
}
def maxProfit(self, k: int, prices: list[int]) -> int:
  n = len(prices)
  if k >= n // 2:
    cash = hold = 0; hold = float('-inf')
    for p in prices:
      cash, hold = max(cash, hold+p), max(hold, cash-p)
    return cash
  T0 = [0]*(k+1); T1 = [float('-inf')]*(k+1)
  for p in prices:
    for j in range(k, 0, -1):
      T0[j] = max(T0[j], T1[j] + p)
      T1[j] = max(T1[j], T0[j-1] - p)
  return T0[k]

Case 1 · k=1 Cloud Spot Instance — Single Reservation Window Infra / Finance

Your team can reserve a cloud spot instance once (commit) and release it once (exit) to minimize cost. Given an hourly cost array, find the maximum cost savings from a single commit-release window compared to always paying on-demand.

EXAMPLE
costs = [0.42, 0.18, 0.31, 0.12, 0.45, 0.38]
Output: 0.33
// commit at 0.12 (hour 4), release at 0.45 (hour 5) → savings 0.33/hr
Constraints: 1 ≤ n ≤ 10⁵, costs are non-negative floats

Why k=1: You get one opportunity to lock in a low price and benefit from it. The running minimum (hold = max(hold, −cost)) tracks the best entry point seen so far. At each step, you check if releasing now beats waiting.

Spot Instance · Single Window
public double maxSavings(double[] costs) {
  double cash = 0, hold = Double.NEGATIVE_INFINITY;
  for (double c : costs) {
    cash = Math.max(cash, hold + c);
    hold = Math.max(hold, -c);
  }
  return cash;
}
def max_savings(costs: list[float]) -> float:
  cash, hold = 0.0, float('-inf')
  for c in costs:
    cash = max(cash, hold + c)
    hold = max(hold, -c)
  return cash
Case 6 · k=∞ + fee API Gateway — Cost Arbitrage with Switching Fee Platform Engineering

Your service routes requests through two API providers whose per-request cost fluctuates each minute. Switching providers incurs a fixed switching fee. Given a cost-difference array (positive = provider A is cheaper), find the maximum savings from optimally switching providers, accounting for switching costs.

EXAMPLE
cost_deltas = [5, 3, 8, 2, 7, 9, 4], fee = 2
Output: 13
// Switch at delta=3 (pay fee), earn through delta=9, switch back (pay fee) → net 13
Constraints: 1 ≤ n ≤ 10⁵, 0 ≤ fee ≤ 100

Why k=∞ + fee: Unlimited switches allowed but each costs a fee. Small delta windows aren't worth it. This is exactly LC #714 — the fee raises the bar for when switching pays off.

API Gateway · Switching with Fee
public int maxSavings(int[] deltas, int fee) {
  int cash = 0, hold = Integer.MIN_VALUE;
  for (int d : deltas) {
    int prev = cash;
    cash = Math.max(cash, hold + d);
    hold = Math.max(hold, prev - d - fee);
  }
  return cash;
}
def max_savings(deltas: list[int], fee: int) -> int:
  cash, hold = 0, float('-inf')
  for d in deltas:
    cash, hold = (
      max(cash, hold + d),
      max(hold, cash - d - fee)
    )
  return cash
Case 5 · k=∞ + cooldown Feature Flag System — Mandatory Stabilization Window Platform Engineering

A feature flag controller enables or disables a feature based on observed error reduction per hour. Due to cache propagation delay, after disabling a feature (sell) you must wait one full hour before re-enabling it (cooldown). Given the hourly error-reduction value when the feature is on, find the optimal enable/disable schedule to maximize total error reduction.

EXAMPLE
values = [1, 2, 3, 0, 2], cooldown = 1 hour
Output: 3
// Enable hours 1-3 (gain +3), cooldown hour 4, re-enable hour 5 (gain +0)
Constraints: 1 ≤ n ≤ 5000, 0 ≤ values[i] ≤ 1000

Why cooldown matters: After disabling (selling), the system is locked for one hour. This temporal coupling means greedy fails — taking a marginal gain today might block a larger gain tomorrow. The prev_cash variable carries the pre-sell state forward exactly two steps.

Feature Flag · Cooldown Window
public int maxReduction(int[] values) {
  int cash = 0, hold = Integer.MIN_VALUE, prevCash = 0;
  for (int v : values) {
    int old = cash;
    cash    = Math.max(cash, hold + v);
    hold    = Math.max(hold, prevCash - v);
    prevCash = old;
  }
  return cash;
}
def max_reduction(values: list[int]) -> int:
  cash, hold, prev = 0, float('-inf'), 0
  for v in values:
    cash, hold, prev = (
      max(cash, hold + v),
      max(hold, prev - v),
      cash
    )
  return cash

Step 1: Write the universal template

Understand the split: cash vs hold. Convince yourself that hold = max(hold, −price) is just tracking the minimum buy price.

07 — MENTAL MODEL

The one question
behind every variant

At each day, the machine asks: given my current state (holding or not), what is the best total profit reachable from here? The DP state is just a compact encoding of that answer.

The three-factor state T[i][k][holding] always compresses to scalars because each row only depends on the previous row. The number of scalars you need equals the number of distinct k-levels you must track — 1 for k=1 or k=∞, 2 for k=2, K for arbitrary k.

Constraints like cooldown and fees don't add new states — they tweak one transition. Cooldown changes which day's cash feeds the buy. Fee changes how much the buy costs. The machine shape stays the same.

The Single Rule
At each day, in each holding-state, take the better of two options: stay as you are, or take the action that transitions you. The constraint (k, cooldown, fee) just modifies what "take the action" costs or requires.
Interview Signal Sentence
"I model this as a two-state DP machine: T[i][k][0] for not holding and T[i][k][1] for holding. At each day, each state takes the max of resting or transitioning. The problem's constraint — whether that's k=1, a cooldown, or a fee — just specializes one of the two transition lines. The code falls out directly from the recurrence."
