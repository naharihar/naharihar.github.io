The Greedy Commit — Local Optimality at Every Step

Greedy algorithms make the best available choice at each step without reconsidering earlier decisions. When the problem has the right structure, this local commitment reaches a global optimum — with no dynamic programming or backtracking required.

01

The Core Insight

Greedy algorithms solve optimization problems by making a locally optimal choice at each decision point and never revisiting it. The trick is that for certain problem structures, you can prove the local choice never forecloses a globally better solution.

Core Insight

Greedy works when two properties hold: the Greedy Choice Property — the optimal solution includes the locally optimal choice — and the Optimal Substructure — an optimal solution to the whole contains optimal solutions to its sub-problems. When both hold, the greedy commit is always safe.

The common pattern is: sort by a key that encodes priority, then sweep through the sorted sequence committing to each item if it satisfies the constraint. The hard intellectual work is identifying what to sort by and proving that the sort order preserves the greedy choice property.

Consider interval scheduling. Why sort by end time and not start time? Because choosing the interval that finishes earliest leaves the maximum remaining time for future intervals. Any other choice leaves strictly less room. This is the elimination argument — by choosing the earliest-ending interval, we dominate all alternative first choices.

Why Greedy is Safe — The Exchange Argument

The standard proof technique is the exchange argument: assume some optimal solution OPT makes a different first choice than our greedy choice G. Show you can swap OPT's first choice for G without making the solution worse. By induction, you can transform OPT into the greedy solution — proving greedy is at least as good as any alternative.

Recognition Shortcuts

Reach for greedy when the problem asks for: minimum number of X to cover all Y, maximum number of non-overlapping events, or minimize total cost/time of a sequence of decisions. If you can state the problem as "always pick the most X item first," greedy almost certainly applies. If you find yourself needing to un-pick a past choice, switch to DP.

The 3 Patterns

Greedy problems cluster into three structural families. Each has a characteristic data structure — sorted array + sweep, two pointers, or a heap — and a characteristic proof that the greedy choice is safe.

Pattern 1

Interval Scheduling Greedy

Sort intervals by end time. Sweep left to right, greedily selecting each interval whose start time doesn't overlap the last selected end. Provably maximizes the count of non-overlapping selections.

435 · Non-overlapping Intervals 452 · Min Arrows to Burst Balloons 253 · Meeting Rooms II 56 · Merge Intervals 1024 · Video Stitching
Pattern 2

Converging Two-Pointer Greedy

Sort the array, place one pointer at each end. At each step, greedily decide whether the largest remaining item can pair with the smallest. Eliminates the need to try all pairings.

881 · Boats to Save People 455 · Assign Cookies 11 · Container With Most Water 392 · Is Subsequence 2410 · Max Matching of Players
Pattern 3

Priority Queue Greedy

Use a max-heap or min-heap to always process the most urgent or most profitable item next. Reduces "which item to pick" from O(n) scan to O(log n) heap extraction.

621 · Task Scheduler 1642 · Furthest Building 767 · Reorganize String 1675 · Minimize Deviation 1405 · Longest Happy String

Greedy Skeleton

Every greedy implementation follows the same shape: sort by a priority key, then sweep and commit.

greedy_skeleton 
// Greedy skeleton — adapt the sort key and condition per problem
public int greedy(int[][] intervals) {
    // Step 1: Sort by the greedy priority key
    Arrays.sort(intervals, (a, b) -> a[1] - b[1]); // sort by end time

    int count = 0;
    int lastEnd = Integer.MIN_VALUE;

    // Step 2: Sweep — commit greedily, never look back
    for (int[] interval : intervals) {
        if (interval[0] >= lastEnd) {   // satisfies constraint
            count++;
            lastEnd = interval[1];          // commit: update state
        }
        // else: skip — this choice was dominated, provably safe to ignore
    }
    return count;
}
# Greedy skeleton — adapt the sort key and condition per problem
def greedy(intervals: list[list[int]]) -> int:
    # Step 1: Sort by the greedy priority key
    intervals.sort(key=lambda x: x[1])  # sort by end time

    count = 0
    last_end = float('-inf')

    # Step 2: Sweep — commit greedily, never look back
    for start, end in intervals:
        if start >= last_end:  # satisfies constraint
            count += 1
            last_end = end      # commit: update state
        # else: skip — dominated choice, safe to ignore

    return count
Most Common Gotcha

Sorting by the wrong key invalidates the greedy choice property. For interval scheduling the sort must be by end time, not start time or duration. Sorting by start time might seem natural but it fails: a short interval starting slightly later can dominate a long one that starts first. Always derive the sort key from the exchange argument, not intuition.

Why Each Skip is Safe

When an interval is skipped because its start time falls inside the current window, every future interval that could co-exist with it can also co-exist with our greedy choice (since our choice ends no later than the skipped interval ends). We lose nothing by committing to the earlier-finishing option.

Deep Dives

These two problems reveal non-obvious structure. Neither is the "textbook" greedy example — both require you to discover the right ordering or decomposition before the greedy move becomes obvious.

Deep Dive 1

135 · Candy Hard

There are n children standing in a line. Each child is assigned a rating value. You must distribute candies to these children such that: each child must have at least one candy, and children with a higher rating than their neighbor must get more candies than that neighbor. Return the minimum number of candies required.

The naive approach — try to satisfy both neighbors simultaneously — leads to circular dependencies. The key is that left-neighbor and right-neighbor constraints are independent and can be solved in separate passes.

Key Insight

Two-pass greedy: Left pass satisfies "must beat left neighbor" in isolation. Right pass (right-to-left) satisfies "must beat right neighbor" in isolation. Take the maximum of both arrays at each index — this simultaneously satisfies both constraints with the minimum candy count.

lc135_candy 
public int candy(int[] ratings) {
    int n = ratings.length;
    int[] left  = new int[n];
    int[] right = new int[n];
    Arrays.fill(left, 1);
    Arrays.fill(right, 1);

    // Left pass: satisfy left-neighbor constraint
    for (int i = 1; i < n; i++) {
        if (ratings[i] > ratings[i - 1])
            left[i] = left[i - 1] + 1; // must beat left neighbor
    }

    // Right pass: satisfy right-neighbor constraint
    for (int i = n - 2; i >= 0; i--) {
        if (ratings[i] > ratings[i + 1])
            right[i] = right[i + 1] + 1; // must beat right neighbor
    }

    // Merge: take the max — satisfies both constraints minimally
    int total = 0;
    for (int i = 0; i < n; i++)
        total += Math.max(left[i], right[i]);

    return total;
}
// Time: O(n) — three linear passes
// Space: O(n) — two auxiliary arrays
def candy(self, ratings: list[int]) -> int:
    n = len(ratings)
    left  = [1] * n
    right = [1] * n

    # Left pass: satisfy left-neighbor constraint
    for i in range(1, n):
        if ratings[i] > ratings[i - 1]:
            left[i] = left[i - 1] + 1  # must beat left neighbor

    # Right pass: satisfy right-neighbor constraint
    for i in range(n - 2, -1, -1):
        if ratings[i] > ratings[i + 1]:
            right[i] = right[i + 1] + 1  # must beat right neighbor

    # Merge: take the max — satisfies both constraints minimally
    return sum(max(l, r) for l, r in zip(left, right))

# Time: O(n) — three linear passes
# Space: O(n) — two auxiliary arrays

The elegance here is the decomposition: two constraints that seem entangled are actually independent when viewed directionally. The left array is a one-way greedy sweep; the right array is a one-way greedy sweep in the opposite direction. The max-merge is then a trivial O(n) operation that satisfies both simultaneously.

Deep Dive 2

406 · Queue Reconstruction by Height Medium

You are given an array people where people[i] = [hi, ki] means the i-th person has height hi and exactly ki people in front of them who are taller or of equal height. Reconstruct the queue in valid order.

This problem looks like it needs backtracking, but has an elegant greedy structure. The trick is noticing that taller people are "invisible" to shorter ones — a shorter person only cares about the positions of people at least as tall.

Key Insight

Sort descending by height, break ties by k ascending. Then insert each person at index k in the result list. Because we process tallest first, inserting at position k is always correct — shorter people inserted later don't affect the k-count of taller people already placed, since shorter people are invisible to taller ones' k constraint.

lc406_queue_reconstruction 
public int[][] reconstructQueue(int[][] people) {
    // Sort: tallest first; ties broken by k ascending
    Arrays.sort(people, (a, b) ->
        a[0] != b[0] ? b[0] - a[0] : a[1] - b[1]
    );

    List<int[]> result = new LinkedList<>();

    // Greedy insert: position k is always correct for the current person
    for (int[] p : people) {
        result.add(p[1], p); // insert at index = k
        // Shorter people inserted later won't affect this k-count
    }

    return result.toArray(new int[people.length][]);
}
// Time: O(n^2) — each LinkedList insertion is O(n)
// Space: O(n) — result list (sorting is in-place)
def reconstructQueue(self, people: list[list[int]]) -> list[list[int]]:
    # Sort: tallest first; ties broken by k ascending
    people.sort(key=lambda x: (-x[0], x[1]))

    result = []

    # Greedy insert: position k is always correct for the current person
    for h, k in people:
        result.insert(k, [h, k])  # insert at index = k
        # Shorter people inserted later won't affect this k-count

    return result

# Time: O(n^2) — each list insert is O(n)
# Space: O(n) — result list

The proof is an exchange argument: if we tried inserting in any other order (e.g., ascending height), inserting a tall person later would shift the k-indices of already-placed shorter people — invalidating their correctness. Processing tallest first makes each insertion independent and idempotent with respect to previous placements.

Real World Problems

Every greedy pattern appears in production engineering problems. These examples use the same interval scheduling, two-pointer, and heap mechanics — but grounded in infrastructure, e-commerce, and SRE contexts you'd actually encounter.

Pattern 1 · Interval Scheduling · Infrastructure / CI-CD

CI/CD Build Agent Slot Optimizer

Your company's CI pipeline has exactly one shared build agent available at a time. You receive n build jobs each with a scheduled [startMinute, endMinute] window. Each job must run without interruption within its window. Find the maximum number of build jobs you can run on this single agent without overlap.

Each job that runs generates revenue (it unblocks a deploy). You want to maximize throughput — the number of jobs completed — not execution time.

Example
jobs = [[0,30],[5,10],[15,20],[10,25],[20,35],[30,40]] → Sort by end: [[5,10],[15,20],[10,25],[0,30],[20,35],[30,40]] → Greedy picks: [5,10], [15,20], [20,35], [30,40] → Output: 4 jobs completed
  • 1 ≤ n ≤ 10⁵
  • 0 ≤ start < end ≤ 10⁶
  • Time: O(n log n)
  • Space: O(1)

Why this pattern?

Sorting by end time and greedily selecting each non-overlapping job is optimal by the exchange argument. Any alternative first choice either ends later (reducing available future time) or starts later (impossible, since we're already choosing the earliest-ending non-conflicting job). The greedy choice dominates all alternatives — each commit is provably safe.

ci_build_slot_optimizer 
public int maxJobsScheduled(int[][] jobs) {
    // Sort by end time — greedy choice property requires this order
    Arrays.sort(jobs, (a, b) -> a[1] - b[1]);

    int count = 0;
    int agentFreeAt = 0; // agent is available from time 0

    for (int[] job : jobs) {
        int start = job[0], end = job[1];

        if (start >= agentFreeAt) {
            // Agent is free — commit to this job
            count++;
            agentFreeAt = end; // agent busy until this job ends
        }
        // else: job overlaps current run — skip, it was dominated
    }
    return count;
}
// Time: O(n log n) for sort; O(n) sweep — total O(n log n)
// Space: O(1) — only two state variables
def max_jobs_scheduled(jobs: list[list[int]]) -> int:
    # Sort by end time — greedy choice property requires this order
    jobs.sort(key=lambda j: j[1])

    count = 0
    agent_free_at = 0  # agent is available from time 0

    for start, end in jobs:
        if start >= agent_free_at:
            # Agent is free — commit to this job
            count += 1
            agent_free_at = end  # agent busy until this job ends
        # else: job overlaps current run — skip, dominated

    return count

# Time: O(n log n) for sort; O(n) sweep — total O(n log n)
# Space: O(1) — only two state variables
Pattern 2 · Converging Two-Pointer Greedy · E-commerce / Fulfillment

Bundle Shipping Container Optimizer

Your fulfillment center ships items paired together to reduce per-shipment fees. Each container holds at most two items and can carry a combined weight of at most W kg. Given n item weights, find the minimum number of containers needed to ship all items.

Shipping containers cost $15 each regardless of how full they are. You want to maximize pairing to minimize total cost.

Example
weights = [1, 2, 3, 4, 5], W = 5 → Sorted: [1, 2, 3, 4, 5] → Pairs: [1,4] → fits (sum=5), [2,3] → fits (sum=5), [5] → alone → Output: 3 containers (minimum)
  • 1 ≤ n ≤ 5×10⁴
  • 1 ≤ weights[i] ≤ W ≤ 3×10⁴
  • Time: O(n log n)
  • Space: O(1)

Why this pattern?

Sort the weights. Use two pointers: lo at the lightest item and hi at the heaviest. If the heaviest item can pair with the lightest (their sum ≤ W), pair them and move both pointers inward — this is the greedily optimal pairing for the heaviest item. If not, the heaviest must ship alone because it can't pair with anyone (every other item is at least as heavy as the lightest, making the sum strictly larger). The elimination is safe: no future pairing could be better for the heaviest item.

bundle_shipping_optimizer 
public int minContainers(int[] weights, int W) {
    Arrays.sort(weights);
    int lo = 0, hi = weights.length - 1;
    int containers = 0;

    while (lo <= hi) {
        if (weights[lo] + weights[hi] <= W) {
            // Heaviest item pairs with lightest — optimal pairing for hi
            lo++;
        }
        // Heaviest ships alone if no pairing possible
        hi--;
        containers++;
    }
    return containers;
}
// Time: O(n log n) sort + O(n) sweep
// Space: O(1)
def min_containers(weights: list[int], W: int) -> int:
    weights.sort()
    lo, hi = 0, len(weights) - 1
    containers = 0

    while lo <= hi:
        if weights[lo] + weights[hi] <= W:
            # Heaviest item pairs with lightest — optimal pairing for hi
            lo += 1
        # Heaviest ships alone if no pairing possible
        hi -= 1
        containers += 1

    return containers

# Time: O(n log n) sort + O(n) sweep
# Space: O(1)
Pattern 3 · Priority Queue Greedy · SRE / Observability

Alert Deduplication Scheduler

Your SRE alerting system receives alerts from n alert types, each with a frequency — the number of times it must fire within the scheduling window. To prevent alert fatigue, the same alert type cannot fire in two consecutive time slots; it needs at least cooldown idle slots between firings. Find the minimum total time slots needed to fire all alerts.

Each idle slot wastes 1 unit of on-call time and must be minimized.

Example
alerts = ['DISK','DISK','DISK','CPU','CPU','MEM'], cooldown = 2 → Frequencies: {DISK:3, CPU:2, MEM:1} → Schedule: DISK CPU MEM DISK CPU _ DISK → Output: 7 time slots (1 idle slot required)
  • 1 ≤ alerts.length ≤ 10⁴
  • alerts[i] is uppercase letter
  • 0 ≤ cooldown ≤ 100
  • Time: O(n)
  • Space: O(1)

Why this pattern?

We need to schedule the most frequent alert as early and as often as possible to prevent it from blocking progress. The math insight: the dominant constraint comes from the most frequent alert type. If its count is f_max, it needs at least (f_max - 1) * (cooldown + 1) slots to fire all its instances. Every other alert type fills in the gaps; any that don't fit create idle slots. We can compute the answer analytically using frequencies — no explicit scheduling needed.

alert_dedup_scheduler 
public int leastInterval(char[] alerts, int cooldown) {
    int[] freq = new int[26];
    for (char a : alerts) freq[a - 'A']++;

    Arrays.sort(freq);
    int maxFreq = freq[25];

    // Count how many alert types share the maximum frequency
    int maxCount = 0;
    for (int f : freq) if (f == maxFreq) maxCount++;

    // Frame formula: (maxFreq-1) full frames + last partial frame
    int frames = (maxFreq - 1) * (cooldown + 1) + maxCount;

    // Can always pack all alerts if total count exceeds frames
    return Math.max(alerts.length, frames);
}
// Time: O(n) to count + O(26 log 26) sort ≈ O(n)
// Space: O(1) — fixed 26-element array
from collections import Counter

def least_interval(alerts: list[str], cooldown: int) -> int:
    freq = sorted(Counter(alerts).values())
    max_freq = freq[-1]

    # Count how many alert types share the maximum frequency
    max_count = freq.count(max_freq)

    # Frame formula: (maxFreq-1) full frames + last partial frame
    frames = (max_freq - 1) * (cooldown + 1) + max_count

    # Can always pack all alerts if total count exceeds frames
    return max(len(alerts), frames)

# Time: O(n) to count + O(26 log 26) sort ≈ O(n)
# Space: O(1) — fixed 26-element frequency array

Mental Model

Think of a greedy algorithm as a contract you sign one clause at a time. Before signing each clause, you ask one question: "Could I ever regret this clause given the remaining options?" If the answer is provably no — because your choice dominates any alternative first step — you sign without hesitation. The exchange argument is the proof that you'll never regret it.

The sorting step is the priority declaration: it arranges all future choices in the order you'll commit to them. Choosing the wrong sort key is like prioritizing the wrong clause — your greedy commits become locally valid but globally wrong. The sort key must match the dominance relation you want to prove. For intervals, end time is dominant because it directly maximizes future flexibility. For pairing by capacity, sorted order makes the two-pointer elimination obvious.

When greedy breaks down, it's almost always because the problem has a dependency structure that makes local choices entangle future ones. If picking item A now changes the cost of item B later, you likely need DP. The signal is that you find yourself wanting to "un-pick" a greedy choice after seeing what comes next.

Most Common Mistake

Applying greedy to a problem with dependencies. Greedy is correct only when each local choice is provably safe in isolation. If the value of your current choice depends on future choices (e.g., "should I take this coin if it might prevent me from completing a larger set later?"), you have a dependency and DP is required. Always ask: "Does making this choice now change the value of future choices?" If yes, reach for DP instead.

The Invariant

The greedy invariant has two parts. (1) Greedy Choice Property: the optimal solution can always be transformed to include the greedy choice without worsening it — proven by exchange argument. (2) Optimal Substructure: after making the greedy choice, the remaining sub-problem has the same optimal structure — so greedy applies recursively.

Interview Sentence — Say This Verbatim

"I'll use a greedy approach sorted by end time. The key insight is that choosing the interval with the earliest end time provably leaves the maximum flexibility for all subsequent choices — any alternative first pick ends no sooner, so it can only dominate or equal our choice, never improve upon it. By the exchange argument, the greedy selection is always in some optimal solution, which means we can commit irrevocably at each step and achieve O(n log n) overall with no backtracking."
