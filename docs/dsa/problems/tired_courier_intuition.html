Tired Courier — build the intuition before the optimization

Start from the brute-force thought process, understand exactly what work is repeated, then earn the binary-search optimization instead of memorizing it.

01 Problem

What are we actually minimizing?

Problem Statement

Given packages at sorted positions pos[] with weights weight[], the courier takes contiguous groups of at most k packages per trip. Trip fatigue = furthest_pos × total_weight. Minimize total fatigue across all trips.

Example
pos[2, 5, 6, 9, 12]
weight[3, 1, 4, 2, 5]
k2
GoalFind grouping that minimizes total fatigue
Human version of the problem Think of the courier making several round trips from home. On each trip, they can carry at most k packages, and because the addresses are already ordered along one road, a trip always takes the next consecutive block of packages. The farther that trip goes and the more total weight it carries, the more tiring it is.

The easy-to-miss constraint Trips must be contiguous. If trip 1 takes packages 0 and 1, trip 2 must start at package 2. You are choosing cut points, not arbitrary subsets.

The answer is not inside the array. We need to find the best way to split packages into trips — and the cost of each split is a non-linear function (position × weight).

02 First Principles

If we knew nothing, what would we try?

The most natural approach: try every way to split packages into valid trips (at most k per trip) and pick the one with minimum total fatigue.

1
Enumerate every possible grouping.

Try all ways to cut the array into contiguous segments of size ≤ k.

2
Compute total fatigue for each grouping.

For each segment [l..r]: fatigue = pos[r] × sum(weight[l..r]).

3
Return the minimum.

Track the minimum total fatigue seen across all valid groupings.

The problem with this approach The number of ways to split n packages into groups of ≤ k is exponential. For n=20, k=5 there are thousands of combinations. For n=1000 it's completely infeasible.
03 Brute Force

A workable but slow solution

We can do better than full enumeration using recursion with memoization — but it's still O(n²k) which is too slow for large inputs.

// Brute-force: try every valid split recursively
class BruteForce {
    public long minTotalFatigue(int[] pos, int[] weight, int k) {
        int n = pos.length;
        // prefix sums for O(1) range weight queries
        long[] prefix = new long[n + 1];
        for (int i = 0; i < n; i++) prefix[i+1] = prefix[i] + weight[i];

        long[] memo = new long[n];
        java.util.Arrays.fill(memo, -1);
        return solve(0, pos, prefix, k, n, memo);
    }

    private long solve(int i, int[] pos, long[] prefix, int k, int n, long[] memo) {
        if (i == n) return 0;
        if (memo[i] != -1) return memo[i];
        long best = Long.MAX_VALUE;
        // try all trip sizes 1..k starting at i
        for (int j = i; j < Math.min(n, i+k); j++) {
            long tripWeight = prefix[j+1] - prefix[i];
            long fatigue = (long) pos[j] * tripWeight;
            long rest = solve(j+1, pos, prefix, k, n, memo);
            best = Math.min(best, fatigue + rest);
        }
        return memo[i] = best;
    }
}
// Time: O(n*k)  Space: O(n)
// Still O(n*k) per query — too slow when n and k are both large
from functools import lru_cache

class BruteForce:
    def min_total_fatigue(self, pos, weight, k):
        n = len(pos)
        prefix = [0] * (n + 1)
        for i in range(n):
            prefix[i+1] = prefix[i] + weight[i]

        @lru_cache(maxsize=None)
        def solve(i):
            if i == n: return 0
            best = float('inf')
            for j in range(i, min(n, i+k)):
                trip_weight = prefix[j+1] - prefix[i]
                fatigue = pos[j] * trip_weight
                best = min(best, fatigue + solve(j+1))
            return best

        return solve(0)

# Time: O(n*k)  Space: O(n)
# Correct but slow when n and k are both large
If you are wondering why we use prefix sums We need the total weight of packages l..r in O(1). Without prefix sums, each call would rescan the range in O(k). Prefix sums give us prefix[r+1] - prefix[l] in O(1) — a minor optimization but good practice.

Wait — we need to re-examine. The brute force finds the true minimum by exploring all paths. The DP memoization merges overlapping subproblems: solve(i) = minimum fatigue to deliver packages i..n-1.

Key observation from the walkthrough The DP correctly finds the optimum, but at the cost of testing k choices at every position. When k is large (e.g. k=100, n=10000), that's 10⁶ operations just for the DP — and we haven't even considered that this cost grows with n.

06 What work are we repeating?

The real question is feasibility, not assignment

In the DP, for every starting index i we ask: "which trip size from 1..k minimizes the total from here?"

But flip the question. Instead of asking "what's the best grouping?", ask: "given a fatigue budget F per trip, can I deliver all packages?"

1
Choose a fatigue cap F.

Try F = 100, then 200, then 150... some cap that might work.

2
Greedily check if F is feasible.

Walk left to right. Keep adding packages to the current trip as long as trip fatigue stays ≤ F and count ≤ k.

3
Find the minimum F that works.

The answer is the smallest F such that canDeliver(F) is true.

We are not optimizing the DP formula. We are replacing the DP entirely with a yes/no feasibility check, and then optimizing how many caps we test.

07 Optimization Insight

The feasibility answers form a monotonic map

If fatigue cap F is feasible, then cap F+1 is also feasible (more budget = at least as easy). If F is infeasible, F-1 is also infeasible. Classic F→T transition.

This is the key shift The fatigue values of packages are not sorted — but the answer space (possible caps F) is monotonic. That is what binary search needs.
08 Binary Search

Optimize the search over fatigue caps

Instead of trying caps one by one from 0 to max, binary search the cap range. Each step: test the midpoint, narrow the range. Total: O(log(P·W)) tests × O(n) greedy scan each.

public class Solution {

    public long minTotalFatigue(int[] pos, int[] weight, int k) {
        // lo: smallest possible fatigue (a single package must fit)
        // hi: worst case — one trip carries all packages
        long lo = 0, hi = (long) pos[pos.length-1] * sum(weight);

        while (lo < hi) {
            long mid = lo + (hi - lo) / 2;
            if (canDeliver(pos, weight, k, mid)) {
                hi = mid;         // feasible — try a tighter cap
            } else {
                lo = mid + 1;    // infeasible — need more budget
            }
        }
        return lo;
    }

    private boolean canDeliver(int[] pos, int[] weight, int k, long maxF) {
        int i = 0, n = pos.length;
        while (i < n) {
            int count = 0; long curWeight = 0;
            while (i < n && count < k) {
                long newWeight = curWeight + weight[i];
                if ((long) pos[i] * newWeight > maxF) break;
                curWeight = newWeight; count++; i++;
            }
            if (count == 0) return false; // stuck — impossible
        }
        return true;
    }

    private long sum(int[] a) {
        long s = 0; for (int x : a) s += x; return s;
    }
}
class Solution:
    def min_total_fatigue(self, pos, weight, k):
        lo, hi = 0, pos[-1] * sum(weight)

        while lo < hi:
            mid = lo + (hi - lo) // 2
            if self.can_deliver(pos, weight, k, mid):
                hi = mid
            else:
                lo = mid + 1
        return lo

    def can_deliver(self, pos, weight, k, max_f):
        i, n = 0, len(pos)
        while i < n:
            count, cur_weight = 0, 0
            while i < n and count < k:
                new_w = cur_weight + weight[i]
                if pos[i] * new_w > max_f: break
                cur_weight, count, i = new_w, count+1, i+1
            if count == 0: return False
        return True

The feasibility check did not change in spirit from the brute-force. The only difference: instead of exploring all DP branches, we ask a single yes/no question O(log(P·W)) times.

09 Comparison

What exactly improved?

DP brute force
O(n·k)
Tries all k trip-end choices at every position. Expensive when k is large.
Binary search + greedy
O(n log PW)
Same O(n) greedy scan, but only log(P·W) ≈ 60 times. No branching.

The DP branched at every package. The greedy never branches — it always extends the current trip greedily. Binary search makes this cheap enough to run dozens of times.

10 Pattern

The reusable lesson

Whenever your DP looks like this:

DP shape that hints at binary search:

for every starting index i:
    for every trip endpoint j in i..i+k:
        best = min(best, cost(i,j) + solve(j+1))

Ask yourself: does canFinish(cap) give F…F…T…T? If yes → binary search the cap, greedy scan for feasibility.

For Tired Courier The per-trip cost formula did not change. The greedy check did not change. Only the way we searched the answer space changed — from O(n·k) DP branching to O(log P·W) binary search iterations.
