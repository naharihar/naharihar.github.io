Exam Score Window — build the intuition before the optimization

Start from the linear scan on a realistic [score, studentId] array. Understand why a single binary search lands on the wrong student. Then see exactly how two searches — one hunting left, one hunting right — find both edges of the score band.

01 Problem

What are we actually finding?

Problem Statement

Given students[][] sorted by students[i][0] (score), with students[i][1] being the student ID, and a target score — return [first, last]: the indices of the first and last student who scored target. Return [-1, -1] if none did.

Data shape — students[i]
students[i][0] → score the sort key — binary search on this
students[i][1] → studentId payload — retrieved after finding the window
The array is sorted by students[i][0]. Student IDs within the same score band are in insertion order — no secondary sort is guaranteed.
Example

Since the array is sorted by score, all 74s form a contiguous block. We need the left edge (first) and right edge (last). Student IDs within the band — [3017, 1182, 4450] — are retrieved by iterating students[first..last][1].

02 First Principles

If we knew nothing, what would we do?

Scan the array once. Check students[i][0] against the target. Record the first and last matching index.

1
Walk left to right, reading students[i][0].

The first index where score == target is our left edge. Continue scanning.

2
Keep overwriting last every time score == target.

When the loop ends, last holds the rightmost index. Both boundaries found in one O(n) pass.

3
Break early when students[i][0] > target.

The array is sorted by score — once we pass target, no more matches are possible.

Note on the 2D shapeThe second column (student ID) is never examined during the search — it is pure payload. We only compare students[i][0]. This is true for both the linear scan and the binary search.
03 Brute Force

The naive linear scan

class BruteForce {
    public int[] scoreWindow(int[][] students, int target) {
        int first = -1, last = -1;
        for (int i = 0; i < students.length; i++) {
            int score = students[i][0];
            if (score == target) {
                if (first == -1) first = i; // first hit
                last = i;                      // keep updating last
            }
            if (score > target) break;      // sorted — no more matches
        }
        return new int[]{first, last};
    }
}
class BruteForce:
    def score_window(self, students, target):
        first, last = -1, -1
        for i, row in enumerate(students):
            score = row[0]                     # students[i][0] = score
            if score == target:
                if first == -1: first = i    # first hit
                last = i                       # keep updating
            if score > target: break         # sorted — exit early
        return [first, last]
This is correct — so why improve it?The scan touches every row up to the last occurrence. Worst case (all students scored the same) it scans all n rows. We know the array is sorted by score — we can exploit that structure with binary search.

05 Complexity

Why linear scan wastes work

Linear scan
O(n)
Reads every row up to the last match. If all 10⁶ students scored 74, scans all 10⁶ rows.
Two binary searches
O(log n)
Each search halves the range every step. 10⁶ rows = 20 comparisons per search = 40 total.
When does the gap matter?A national exam with n = 10⁶ students. All scored 74. Linear scan: 10⁶ row reads. Two binary searches: 40 comparisons. The sorted structure is free speedup — not using it is wasteful.
06 Why one binary search isn't enough

A single search lands on the wrong student

Standard binary search on our array: lo=0, hi=8, mid=4. students[4][0]=74 — hit. It returns index 4 immediately. That's student #4450 — the last 74. We have no idea students #3017 and #1182 also scored 74.

The fix — don't stop on a hit, keep goingWhen we find score==target at mid, save the index and continue searching. For the first position push hi = mid - 1 (explore left). For the last push lo = mid + 1 (explore right). The loop keeps narrowing until nothing is left — the last saved index is the answer.
07 The Two Templates

Side by side — what changes and what doesn't

Template 1 — Find FIRST (hunt left)
int lo=0, hi=n-1, first=-1;
while(lo <= hi) {
  int mid = lo+(hi-lo)/2;
  int s = students[mid][0];
  if      (s < target) lo=mid+1;
  else if(s > target) hi=mid-1;
  else {
    first=mid;     // save
    hi=mid-1;      // go LEFT
  }
}
return first;
Template 2 — Find LAST (hunt right)
int lo=0, hi=n-1, last=-1;
while(lo <= hi) {
  int mid = lo+(hi-lo)/2;
  int s = students[mid][0];
  if      (s < target) lo=mid+1;
  else if(s > target) hi=mid-1;
  else {
    last=mid;      // save
    lo=mid+1;      // go RIGHT
  }
}
return last;

The < and > branches read students[mid][0] in both templates — identical. The only difference is the else (hit) branch direction.

Why hi = mid-1 finds FIRST and lo = mid+1 finds LASTOn a hit at mid: pushing hi = mid-1 says "there may be an earlier student with the same score to the left — go check." We already saved mid, so if nothing is earlier, mid is our answer. Pushing lo = mid+1 says the opposite. Same mechanism, mirrored direction. The student ID column plays no role in either decision.

10 Pattern

The reusable lesson

Generalizing to any [key, payload] arrayThis exact pattern applies whenever your data is sorted by a key column and you need a range of matching rows. The binary search only touches the key column. The payload (student ID, product name, transaction amount — anything) is retrieved after the window is found.

The one-line rule for the hit branch

GoalOn hit: students[mid][0] == targetWhy
Find firstans = mid; hi = mid - 1Save, search left for an earlier match
Find lastans = mid; lo = mid + 1Save, search right for a later match
Find anyreturn midStop immediately — just need existence
