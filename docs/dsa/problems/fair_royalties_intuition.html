Fair Royalties — build the intuition before the optimization

The squared cost function looks intimidating. Strip it away, see the familiar pattern underneath, then add it back.

01 Problem

What are we actually minimizing?

Problem Statement

Split n chapters (page counts pages[]) into exactly k contiguous parts. Each part's royalty = (sum of pages)². Minimize the maximum royalty.

Example
pages[4, 3, 2, 5, 1, 6]
k3
GoalMinimize the max part royalty (sum²)
Human version of the problem Imagine a publisher splitting one book into exactly k printed volumes. Each volume gets a royalty bill based on the square of its total pages. Your job is to place the cut points so that the most expensive volume is as cheap as possible.
What is fixed?What can we choose?What are we minimizing?
Chapter order, page counts, and exactly k contiguous partsWhere the k-1 cut points goThe largest royalty among the parts
Why the square changes the feel of the problem
Part A
sum = 5 pages → royalty = 5² = 25
Part B

Takeaway
doubling pages quadruples royalty, so large parts get punished heavily
The easy-to-miss constraint You are not allowed to reorder chapters. This is still a contiguous partition problem, just like Split Array Largest Sum — the square only changes how we measure the cost of each part.

The square makes the cost non-linear — a part twice as long costs four times as much. This makes it impossible to just greedily balance parts by page count.

02 First Principles

Simplify: what if the cost were linear?

Forget the square for a moment. If royalty = sum of pages (not squared), this is exactly LC 410 Split Array Largest Sum. We'd binary search the max sum cap, greedily extend each part until the next chapter would exceed it.

Now add the square back. The only thing that changes in the greedy: instead of checking sum ≤ cap, we check sum² ≤ cap, which is the same as sum ≤ √cap.

The square is just a change of units Binary search over royalty R = sum². Greedy check: extend current part while prefix_sum² ≤ R. The feasibility structure is identical to the linear case.
03 Brute Force

The naive solution: try every split

// Brute-force DP: try every split point
class BruteForce {
    public long minMaxRoyalty(int[] pages, int k) {
        int n = pages.length;
        long[] prefix = new long[n+1];
        for (int i = 0; i < n; i++) prefix[i+1] = prefix[i] + pages[i];

        // dp[i][j] = min max royalty using first i chapters with j parts
        long[][] dp = new long[n+1][k+1];
        for (long[] row : dp) java.util.Arrays.fill(row, Long.MAX_VALUE / 2);
        dp[0][0] = 0;

        for (int j = 1; j <= k; j++) {
            for (int i = j; i <= n; i++) {
                for (int m = j-1; m < i; m++) {
                    long s = prefix[i] - prefix[m];
                    long royalty = s * s;
                    dp[i][j] = Math.min(dp[i][j], Math.max(dp[m][j-1], royalty));
                }
            }
        }
        return dp[n][k];
    }
}
// Time: O(n²k)  Space: O(nk) — too slow for n=10⁴
class BruteForce:
    def min_max_royalty(self, pages, k):
        n = len(pages)
        prefix = [0] * (n+1)
        for i in range(n): prefix[i+1] = prefix[i] + pages[i]

        INF = float('inf')
        dp = [[INF]*(k+1) for _ in range(n+1)]
        dp[0][0] = 0

        for j in range(1, k+1):
            for i in range(j, n+1):
                for m in range(j-1, i):
                    s = prefix[i] - prefix[m]
                    dp[i][j] = min(dp[i][j], max(dp[m][j-1], s*s))
        return dp[n][k]

# Time: O(n²k)  Space: O(nk)

The DP is correct but O(n²k). For n=10⁴, k=100, that's 10¹⁰ operations — completely infeasible.

Key observation from the walkthrough We are not trying to find the optimal split directly. We just need to know: "is there any valid split where every part's royalty ≤ R?" This yes/no question is much cheaper to answer.
05 Complexity

Why does the DP get expensive?

DP brute force
O(n²k)
For every (chapter, part) pair, tries all possible previous split points.
Binary search + greedy
O(n log S²)
~100 binary search iterations × O(n) greedy with prefix sum O(1) lookups.
06 Repeated Work

What work are we repeating?

In the DP, for every chapter index i and part count j, we scan all possible last split points m. This explores all possible histories of splits to find the best one.

But we don't need the best split. We need to answer: "given royalty cap R, can I split into ≤ k parts each with royalty ≤ R?" This is a single left-to-right pass — O(n) — using a greedy.

1
Choose a royalty cap R.

Binary search over possible values of R.

2
Greedy check using prefix sums.

Walk left to right. Extend the current part while sum² ≤ R. Close the part when the next chapter would exceed it. Use prefix sums for O(1) range sums.

3
Count parts used.

If parts ≤ k → feasible. Binary search then narrows R.

07 Optimization Insight

The feasibility answers are monotonic

If royalty cap R is feasible, R+1 is also feasible. If R is infeasible, R-1 also is. The familiar F→T shape.

The key shift Chapter page counts are not sorted — but the royalty caps form a monotonic answer space. Binary search the caps; greedy + prefix sums checks each one in O(n).
08 Why prefix sums?

The role of prefix sums in the greedy

During the greedy scan, we need to know the sum of chapters from start to end. Without prefix sums, each check re-sums the range — O(n) per check × O(n) checks per feasibility call = O(n²) per binary search step.

With prefix sums built once in O(n), each range sum is O(1): prefix[end+1] - prefix[start]. The entire feasibility check drops to O(n).

The combination Binary search handles the search over answer space (which cap R to try). Prefix sums make each feasibility check O(n) instead of O(n²). Together: O(n log S²) total.
09 Comparison

What exactly improved?

DP brute force
O(n²k)
Tries every split point for every (chapter, part) pair. Stores all subproblem results.
Binary search + greedy
O(n log S²)
~120 iterations × O(n) greedy. No DP table. O(n) prefix array only.

The DP found the optimal split. The greedy never finds the split — it just answers "feasible or not?" That's all binary search needs.

10 Pattern

The reusable lesson

DP shape that hints at binary search:

for every (i, j) in (chapters, parts):
    for every split point m:
        dp[i][j] = min(dp[i][j], max(dp[m][j-1], cost(m+1..i)))

When cost() is monotone increasing in range length → binary search the cost cap, greedy for feasibility.

For Fair Royalties The squared cost is monotone in range length (more pages = higher royalty — always). That's the only property binary search needs. The square is irrelevant to the algorithm structure; it's just a number we compare against the cap.
