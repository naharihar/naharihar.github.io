Exam Scheduling — build the intuition before the optimization

Two algorithms meet here: binary search handles "how many hours?", EDF (Earliest Deadline First) handles "is it possible?". Understand each separately, then see why they combine perfectly.

01 Problem

What are we actually minimizing?

Problem Statement

Each student i can only take an exam during [start[i], end[i]]. The school has r rooms (each handles 1 student per hour). Find the minimum number of hours T to schedule everyone.

Example
windows[[0,2],[0,1],[1,3],[2,4],[3,4]]
r2
GoalMinimum T such that everyone can be scheduled in hours 0..T-1

The key difficulty: students have individual availability windows. Opening more hours doesn't always help if students' windows are short. You cannot reschedule — a student must be assigned within their window.

02 First Principles

If we knew nothing, what would we try?

For a fixed T, try all possible assignments of students to time slots. This is an assignment problem — NP-hard in general. But our structure (interval windows + uniform room capacity) admits a greedy solution.

1
Try T = 1, 2, 3, ... hours.

For each T, check if it's possible to schedule all students in hours 0..T-1.

2
For each T, exhaustively try all assignments.

Assign each student to some valid hour. Check if any assignment works with ≤ r students per hour.

3
Return the first T that works.

Since we try T in increasing order, the first valid T is the minimum.

Problem with this approach The number of possible assignments is exponential (each student has multiple valid slots). For n=50 students, this is completely infeasible.
03 The EDF Insight

You don't need to try all assignments

For a fixed T, the best strategy is Earliest Deadline First (EDF): at each hour, among all available unscheduled students, always schedule the ones whose window ends soonest.

The intuition: if student A has window [1,2] and student B has window [1,5], and we can only fit one at hour 1 — schedule A. B has more future options; A has only one. Delaying A risks missing their only slot.

EDF is provably optimal for feasibility This is a classical result in scheduling theory (Jackson's rule, 1955). If any valid schedule exists for time T, EDF will find one. You never need to try other strategies.

04 Brute Force

The naive solution: try every T with EDF

// Brute force: try every T from 1 to n
import java.util.*;
class BruteForce {
    public int minHours(int[][] windows, int r) {
        for (int T = 1; T <= windows.length; T++) {
            if (canScheduleEDF(windows, r, T)) return T;
        }
        return windows.length;
    }

    private boolean canScheduleEDF(int[][] windows, int r, int T) {
        PriorityQueue<int[]> heap = new PriorityQueue<>((a,b) -> a[1]-b[1]);
        int[][] sorted = windows.clone();
        Arrays.sort(sorted, (a,b) -> a[0]-b[0]);
        int idx = 0, scheduled = 0;
        for (int h = 0; h < T; h++) {
            while (idx < sorted.length && sorted[idx][0] <= h) heap.offer(sorted[idx++]);
            while (!heap.isEmpty() && heap.peek()[1] < h) heap.poll();
            for (int s = 0; s < r && !heap.isEmpty(); s++) { heap.poll(); scheduled++; }
        }
        return scheduled == windows.length;
    }
}
// Time: O(n² log n) — tries all T values, each EDF check O(n log n)
import heapq

class BruteForce:
    def min_hours(self, windows, r):
        for T in range(1, len(windows) + 1):
            if self.can_schedule_edf(windows, r, T):
                return T
        return len(windows)

    def can_schedule_edf(self, windows, r, T):
        sorted_w = sorted(windows, key=lambda x: x[0])
        heap, idx, scheduled = [], 0, 0
        for h in range(T):
            while idx < len(sorted_w) and sorted_w[idx][0] <= h:
                heapq.heappush(heap, sorted_w[idx][1])
                idx += 1
            while heap and heap[0] < h:
                heapq.heappop(heap)
            for _ in range(r):
                if not heap: break
                heapq.heappop(heap)
                scheduled += 1
        return scheduled == len(windows)

# Time: O(n² log n)  Space: O(n)

The brute force is correct: it tries T=1, 2, 3,... and stops at the first T where EDF succeeds. The waste: each run from T=1 to T=answer-1 is a failed EDF check that we throw away.

05 Complexity

Why does linear scan waste work?

Brute force
O(n² log n)
n possible T values × O(n log n) EDF check each. Redundant for early T values that obviously fail.
Binary search
O(n log²n)
log n T candidates × O(n log n) EDF. Factor of n improvement.

The EDF check itself is not the bottleneck — it's always O(n log n). The bottleneck is how many times we run it. The brute force runs it n times; binary search runs it log n times.

06 Repeated Work

What work are we repeating?

The brute force runs EDF for T=1, T=2, ..., T=answer. For small T values that obviously fail (T=1 when there are 10 students and r=1), we do a full O(n log n) EDF check just to confirm it fails.

The key insight: can we skip ahead to a better T candidate?

Yes — because the feasibility is monotone. If T=3 fails, T=2 also fails. If T=7 works, T=8 also works. Binary search exploits this to test only ~log n candidates.

The key shift The student windows are not sorted — but the feasibility across possible T values is monotone. Binary search finds the first T where EDF succeeds, testing only log n candidates.
08 Why EDF + Binary Search?

The two algorithms are independent

Binary search answers: which T to test? It narrows the T range in half each step.

EDF answers: is this T feasible? Given T, it greedily schedules students in the optimal order.

1
Binary search picks a candidate T.

Sets lo=1, hi=n, tests mid = (lo+hi)/2 each iteration.

2
EDF checks if T is feasible in O(n log n).

Scans hours 0..T-1, uses a min-heap to always schedule the earliest-deadline student available.

3
Binary search adjusts based on EDF result.

If feasible → try smaller T (hi = mid). If infeasible → try larger T (lo = mid+1).

09 Comparison

What exactly improved?

Brute force
O(n² log n)
Runs EDF for every T from 1 to answer. Most checks are wasted on clearly infeasible T values.
Binary search
O(n log²n)
Runs EDF only ~log n times. Same EDF check, dramatically fewer calls.

The EDF algorithm is unchanged. Binary search simply reduces from n to log n the number of times we call it.

10 Pattern

The reusable lesson

Brute-force shape that hints at binary search:

for T = 1, 2, 3, ..., n:
    if canSchedule(T):   // O(n log n) EDF check
        return T          // first T that works

Since canSchedule(T) is monotone, binary search finds the first T with O(log n) calls instead of O(n).

For Exam Scheduling EDF did not change. The feasibility check did not change. Only the number of T values tested changed — from O(n) to O(log n). The factor of n improvement in outer iterations, combined with the O(n log n) inner check, gives the final O(n log²n).
