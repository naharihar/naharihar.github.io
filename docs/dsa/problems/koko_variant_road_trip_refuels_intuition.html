Road Trip Refuels — build the intuition before the optimization

Start from the brute-force thought process, understand exactly what work is repeated, and then earn the binary-search optimization instead of memorizing it.

01 Problem

What are we actually minimizing?

Problem Statement

You drive across n city legs. Leg i is miles[i] long. Your tank holds k miles — you refuel once before each leg if needed, using one refuel stop per leg. Return the minimum tank capacity k such that you can complete all legs in at most h refuel stops.

Example
Inputmiles = [3, 6, 7, 11], h = 8
Output4

The important subtlety: the answer is not inside the input array. We are looking for the smallest tank size that satisfies a constraint on total refuel stops.

02 First Principles

If we knew nothing about binary search, what would we do?

The most natural idea: try every possible tank size, starting from the smallest.

1
Pick a candidate tank size.

Start with k = 1, then 2, then 3, up to max of the input array.

2
Compute how many refuel stops that rate needs.

For each group of size s at rate k, we need ⌈s / k⌉ refuel stops. Sum over all road legs.

3
Return the first rate that works.

Since we try rates in increasing order, the first valid one is the minimum answer.

The brute-force algorithm: test every k from 1 to max(input), stop at the first one where total refuel stops ≤ h.

03 Brute Force

The naive solution is completely reasonable

class Solution {
    public int minTankSize(int[] miles, int h) {
        int max = 0;
        for (int m : miles) max = Math.max(max, m);
        for (int k = 1; k <= max; k++) {
            int stops = 0;
            for (int m : miles) stops += (m + k - 1) / k;
            if (stops <= h) return k;
        }
        return max;
    }
}
import math
class Solution:
    def min_tank_size(self, miles, h):
        for k in range(1, max(miles) + 1):
            if sum(math.ceil(m / k) for m in miles) <= h:
                return k
If you are wondering about (size + k - 1) / k This is integer ceiling division. If a group has 10 items and you process k=3 per refuel stop, you need ⌈10/3⌉ = 4 refuel stops. Plain division gives 3. The expression (10 + 3 - 1) / 3 = 4 rounds up correctly without floating point.

This code reflects the direct reasoning: "what is the smallest tank size that works?"

Why return on total ≤ h? The problem asks us to finish within h refuel stops. Equal is valid — there's a spare slot. Less is also fine.
05 Complexity

Why does brute force get expensive?

Candidate rates tried
1 … max(input)
If the largest group is huge, we try millions of candidates one by one.
Work per candidate
O(n)
Each candidate scans all road legs to compute total refuel stops.
Total: O(n × max(input)) For max = 10⁹, n = 10⁵ → 10¹⁴ operations. Completely infeasible.
06 Repetition

What work are we repeating?

For every candidate rate k, we ask the same yes/no question:

Repeated check

canDrive(k) = totalRefuelStops(k) <= h ?

1
Choose a candidate rate.

k = 1, then 2, then 3…

2
Recompute total refuel stops for every group.

The full scan of all road legs happens again for each candidate.

3
Check true or false.

Does this rate finish within h refuel stops or not?

We are not optimizing the formula. We are optimizing how many candidate rates we need to test.

07 Optimization Insight

The answers form a monotonic map

If rate k works, k+1 also works — a higher rate finishes faster. If k fails, k-1 also fails. The pattern: F F F… T T T. Classic binary-search shape.

This is the key shift The input array is not sorted — but the answer space (rates 1 … max) is monotonic. That is what binary search needs.
08 Binary Search

Optimize the search over road legs

Instead of testing every rate one by one, binary search the range 1 … max(input). Ask the same feasibility question only for midpoint candidates.

class Solution {
    public int minTankSize(int[] miles, int h) {
        int lo = 1, hi = 0, ans = 0;
        for (int m : miles) hi = Math.max(hi, m);
        ans = hi;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (canDrive(miles, mid, h)) { ans = mid; hi = mid - 1; }
            else lo = mid + 1;
        }
        return ans;
    }
    private boolean canDrive(int[] miles, int k, int h) {
        int stops = 0;
        for (int m : miles) stops += (m + k - 1) / k;
        return stops <= h;
    }
}
import math
class Solution:
    def min_tank_size(self, miles, h):
        lo, hi, ans = 1, max(miles), max(miles)
        while lo <= hi:
            mid = lo + (hi - lo) // 2
            if sum(math.ceil(m / mid) for m in miles) <= h:
                ans = mid; hi = mid - 1
            else: lo = mid + 1
        return ans

We still compute total refuel stops the same way. The optimization is that we test only log(max) candidate rates instead of every rate from 1 to max.

09 Comparison

What exactly improved?

ApproachCandidates testedWork per candidateTotal
Brute forcemax(input) — every k one by oneO(n)O(n × max)
Binary searchlog(max) — halves the range each stepO(n)O(n log max)
Concrete numbers max = 10⁹, n = 10⁵ → Brute force: 10¹⁴ ops (infeasible). Binary search: log₂(10⁹) × 10⁵ ≈ 30 × 10⁵ = 3×10⁶ ops (fast).
10 Pattern

The reusable lesson

Brute-force shape that signals binary search on answer:

for every possible answer k:
    if checkFeasibility(k):
        return k

Ask: do the feasibility results form F F F … T T T?
If yes → binary search the answer space instead of scanning it.

For Road Trip Refuels The ceiling-division formula did not change. The feasibility check did not change. Only the way we searched the candidates changed — from O(max) linear scan to O(log max) binary search.
