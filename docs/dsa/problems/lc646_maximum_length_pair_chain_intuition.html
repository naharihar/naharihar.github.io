First Principles

How to recognize Pair Chain as interval scheduling

This problem becomes much easier the moment you notice that each pair is really just an interval with a different name.

LC 646Pattern 1Strict chain rule
Human Version

The input says “pairs,” but the structure says “intervals”

Translation

[a, b] is just an interval starting at a and ending at b.

The chain condition b < c simply means the next interval must start after the current one ends.

Brute Force

The naive plan is to recursively try every compatible continuation

You could sort the pairs and, from each current pair, try every later pair that can legally follow it. That is enough to understand the structure, but it repeatedly recomputes “best chain starting after this ending value.”

Choose a pairTreat it as the current end boundary.
Try every valid next pairAny pair with start greater than that boundary is a candidate.
Take the best branchThe branching factor becomes expensive quickly.
Optimization

Once translated, the same earliest-finish greedy rule applies

Optimization insight Among candidate pairs that could be chosen next, the one that ends earliest can never be worse for the future than one that ends later.

That is exactly the same exchange argument as non-overlapping intervals. The only wrinkle is the strict inequality: touching endpoints do not count as a valid chain extension.

Spot It

Watch for disguised intervals

If the input is written as pairs, segments, jobs, or even “before/after” constraints, but the real rule is still “can this finish before the next one starts?”, try translating it into interval scheduling first.
